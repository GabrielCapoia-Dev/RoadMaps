# 1. Contexto do projeto

O projeto é uma plataforma para criação de roadmaps de estudo, onde o usuário poderá criar seu próprio roadmap com temas completamente variados, seguindo diferentes padrões e formatos de roadmaps, fluxogramas e trilhas de conhecimento, de forma dinâmica, visual, intuitiva e fácil de usar.

A proposta central da plataforma é permitir que o usuário estruture, compartilhe e acompanhe caminhos de aprendizado, tanto para uso pessoal quanto para colaboração com outras pessoas.

O sistema deve funcionar como uma mistura de:

- editor visual de roadmap;
- plataforma de estudos;
- comunidade de compartilhamento de conhecimento;
- vitrine de roadmaps públicos;
- ambiente colaborativo de evolução e troca de experiência.

# 2. Objetivo principal da plataforma

A plataforma deve permitir que usuários:

- criem roadmaps personalizados;
- organizem trilhas de estudo;
- personalizem a aparência e estrutura desses roadmaps;
- acompanhem o progresso de conclusão;
- compartilhem seus roadmaps com outras pessoas;
- publiquem roadmaps para a comunidade;
- descubram conteúdos e trilhas criadas por outros usuários;
- interajam com a comunidade em torno de aprendizado, estudo e evolução.

A ideia principal é que o sistema seja uma comunidade de estudos, onde pessoas compartilham:

- conhecimento;
- técnicas de estudo;
- experiências;
- recomendações;
- trilhas prontas;
- sequências de aprendizagem;
- materiais e links úteis.

# 3. Filosofia do projeto

A filosofia central da plataforma é:

"Compartilhar conhecimento, técnicas de estudo e trilhas de aprendizado, permitindo que pessoas com mais experiência possam mostrar o caminho para outras, ajudando-as a aprender de forma mais clara, organizada e eficiente."

A plataforma deve transmitir os seguintes valores:

- clareza;
- comunidade;
- evolução;
- colaboração;
- criatividade;
- acessibilidade;
- organização;
- progressão;
- conexão entre conteúdos;
- facilidade de uso.

Ela deve incentivar que o usuário:

- aprenda melhor;
- ensine melhor;
- compartilhe o que sabe;
- siga trilhas já estruturadas;
- crie novas trilhas;
- descubra novos caminhos de estudo.

# 4. Funcionalidades principais esperadas

## 4.1. Criação e edição de roadmaps

A plataforma deverá permitir:

- criar roadmaps do zero;
- montar fluxos visualmente;
- clicar e arrastar os nodes;
- mover nodes livremente;
- conectar nodes entre si;
- criar árvores que se dividem em múltiplos caminhos;
- criar ramificações;
- editar títulos dos nodes;
- editar descrições;
- adicionar conteúdos;
- reorganizar a estrutura livremente;
- excluir nodes;
- duplicar nodes;
- criar diferentes tipos de nodes;
- criar diferentes tipos de conexão.

O editor deve ser extremamente visual e trabalhar prioritariamente com interações de clicar, arrastar e soltar.

## 4.2. Personalização visual

O usuário deverá poder:

- personalizar cores;
- personalizar formato dos nodes;
- escolher estilos diferentes para nodes;
- personalizar conexões;
- diferenciar visualmente tipos diferentes de conteúdo;
- criar roadmaps com identidade própria.

Apesar dessa personalização, a interface da plataforma em si deve sempre permanecer coerente com o design system da BreadCrumbs.

## 4.3. Conteúdo dos nodes

Os nodes poderão representar diferentes tipos de conteúdo.

Por exemplo:

- módulo;
- etapa;
- tarefa;
- recurso;
- marco;
- conteúdo;
- objetivo;
- projeto;
- checkpoint.

Um node poderá possuir informações como:

- título;
- descrição;
- links externos;
- materiais de estudo;
- referências;
- observações;
- progresso;
- estado de conclusão;
- obrigatoriedade;
- posição no roadmap.

A estrutura deve ser preparada para permitir novos tipos de nodes futuramente.

## 4.4. Links e materiais

O usuário poderá adicionar aos nodes:

- links de artigos;
- vídeos;
- documentação;
- cursos;
- livros;
- sites;
- ferramentas;
- repositórios;
- outros materiais úteis.

## 4.5. Progresso

O sistema deverá permitir acompanhamento do progresso.

Por exemplo:

- node não iniciado;
- node em andamento;
- node concluído;
- roadmap com percentual geral de conclusão;
- quantidade de etapas concluídas;
- quantidade de etapas restantes.

O progresso deve ser apresentado visualmente de forma clara.

# 5. Compartilhamento e permissões

O usuário poderá compartilhar um roadmap com outras pessoas.

O compartilhamento deverá possuir níveis de permissão.

Por exemplo:

- Proprietário
- Editor
- Comentador
- Visualizador

O proprietário controla o roadmap.

Um editor poderá colaborar na construção.

Um comentador poderá participar de discussões sem alterar a estrutura.

Um visualizador poderá apenas consumir o conteúdo.

A arquitetura deve ser preparada para um sistema robusto de permissões.

Quando isso acontecer, o roadmap poderá aparecer na área de exploração da plataforma.

# 10. Cadastro do usuário

O usuário deverá poder criar uma conta.

O fluxo esperado é:

1. usuário realiza cadastro;
2. sistema envia um e-mail de confirmação;
3. usuário confirma o e-mail;
4. conta é validada;
5. usuário pode acessar a plataforma.

A arquitetura deve ser preparada para confirmação segura de e-mail.

# 13. Tipos de estrutura

Os roadmaps poderão assumir formatos variados.

Exemplos:

Roadmap linear:

A → B → C → D

Roadmap com ramificações:

        B
       /
A → C
       \
        D

Estruturas maiores:

        B → D
       /
A → C → E → G
       \
        F

Também poderão existir estruturas independentes ou conexões opcionais.

Não modele o sistema supondo que todo roadmap será simplesmente uma lista ordenada.

Pense no roadmap como um grafo de nodes e conexões.

# 23. Arquitetura do backend

O backend será feito com NestJS.

Quero uma arquitetura organizada, robusta e preparada para crescimento.

As regras de negócio devem ficar principalmente nos Services.

Controllers devem ser enxutos.

Fluxo conceitual:

Controller
    ↓
Service
    ↓
Repository
    ↓
Persistência

Organize os recursos por domínio.

Exemplo conceitual:

src/
├── modules/
│   ├── users/
│   ├── authentication/
│   ├── roadmaps/
│   ├── community/
│   └── ...
├── common/
├── config/
├── infrastructure/
└── main.ts

Não é obrigatório seguir exatamente essa estrutura se houver uma alternativa melhor dentro das convenções do NestJS.

Se escolher outra abordagem, documente a decisão.
